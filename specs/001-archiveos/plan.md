# Implementation Plan: ArchiveOS — tactile shelf file search

**Branch**: `001-archiveos` | **Date**: 2026-11-11 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/001-archiveos/spec.md`

## Summary

A Tauri v2 app whose whole UI is one static page (`app/index.html`) plus one plain script (`app/core.js`) holding all testable logic and the demo dataset. The page uses the Rust backend when it runs inside Tauri, and the demo data when opened straight from disk. On macOS the backend asks Spotlight (`mdfind`) for name and content matches, one query per expanded term, and scores files by how many terms hit. It pulls match snippets from Spotlight's own extracted text (`mdimport -t -d3`). Native actions run `open`, `open -R` and `qlmanage -p`. On iOS it walks the app's Documents folder and matches names and plain-text contents.

## Technical Context

**Language/Version**: JavaScript (ES2022, no build step); Rust stable (1.9x) for the backend

**Primary Dependencies**: Tauri 2 (`tauri`, `tauri-build`), `serde`/`serde_json`. Dev: `@tauri-apps/cli`, `@playwright/test` (driving the installed Google Chrome)

**Storage**: None. Spotlight is the index; there is no app database.

**Testing**: `node --test` (logic in `core.js`), `cargo test` (query building, validation, snippet parsing), Playwright (UI acceptance flows against the demo dataset)

**Target Platform**: macOS 13+ (Apple Silicon for text-in-image search); iOS 17+ (Documents folder only)

**Project Type**: desktop app with a mobile target

**Performance Goals**: 60 fps shelf with 108 boxes (36 × 3 copies); search results under 1 s on demo data and under ~2 s via Spotlight

**Constraints**: Works offline; no opacity animation; page must work from `file://` (so classic scripts, not ES modules)

**Scale/Scope**: One user; result lists capped at 300 files

## Complexity Tracking

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| `@playwright/test` dev dependency | Constitution II requires every acceptance scenario to have an automated test; most scenarios are UI flows (sheet expands, shelf filters, inspector opens) | Node has no DOM. A hand-rolled in-page test harness would be more code and less reliable. Using the installed Chrome (`channel: 'chrome'`) avoids a browser download. |
| Two frontend files instead of the brief's single `index.html` | Logic must be importable by `node --test` | Extracting script blocks out of HTML in tests is fragile. A classic `<script src>` still works from `file://`. |
